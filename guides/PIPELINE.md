# Pipeline contract

All mirror content is generated by the pipeline; every fix must land there, not in
an individual file. `docs/`, `versioned_docs/`, `i18n/`, `sidebars.ts` and
`versioned_sidebars/` are all outputs.

**The three additional sections are pipeline outputs too**: `hardware/`, `blog/`
and `changelog/` are no longer treated as HEAD source data. The old 31-stage
pipeline had no stage fetching these three sections, so they stayed at a stale
snapshot for a long time. Now, after `fetch-upstream`, there are three stages —
`fetch-hardware` / `fetch-blog` / `fetch-changelog` (run in bump/refresh/cold-start
modes) — that fetch respectively from the Hardware Guides section of the official
`llms.txt` (256 direct `.md` links + `/hardware/` HTML categories), the Recent
posts of the rendered `/blog/` page, and the slugs discovered from `/changelog/`
and paginated HTML. They write `data/manifests/{hardware,blog,changelog}.json`
(`generated_at`, `source_url`/`sha256`/`bytes` per item) and a `source` plus a
run-level `captured_at` into every md file. When data is missing, **re-run those
three stages** rather than restoring a stale HEAD snapshot with `git checkout --
hardware blog changelog`. After `materialize`, `backfill-captured-at-<version>`
(7.26/7.25/7.24) backfills `captured_at` in the docs tree.

**Still HEAD source data**: `static/img/`, `static/assets/`, like `versions.json` /
`sidebars.ts`, must be preserved; if deleted by mistake, restore them from HEAD
with `git checkout -- static/img static/assets` (do not copy from a drill or
archived directory). `npm run verify:build-inputs` fails closed before the build:
for the three sections it asserts slug-by-slug alignment with the new manifests,
that every md file has `source` + `captured_at` equal to this run's
`generated_at`, and that the newest changelog slug is not older than the official
index (currently `2026-11-17`); `static/img/` ≥1700 and `static/assets/` ≥60 files
are still asserted as lower bounds (`tools/build/index.mjs` calls the same gate at
its start). These two `static/` subtrees hold images and downloadable
attachments: if they are wiped, `/img/` and `/assets/` references in the artifact
will 404 across the board and `asset-refs` / `orphan-assets` / `base-url-refs` /
`llms-links` will all fail in turn.

**The favicon is also a pipeline output (the only exception to the HEAD-restore
rule above)**: `docusaurus.config.ts` deliberately does not declare `favicon:`;
instead `headTags[0]` injects `${sharedAssetBaseUrl}img/favicon.svg`, so the bytes
of `static/img/favicon.svg` are the entire contract — do not switch back to the
`favicon:` field (locale and slim builds would still 404). The `fetch-favicon`
stage after `fetch-upstream` derives the official homepage from
`config/mirror.yml#source.base_url`, parses `<link rel=icon href>` and fetches the
real SVG, writing `static/img/favicon.svg` and `data/manifests/favicon.json`
(`schema`/`generated_at`/`source_url`/`url`/`sha256`/`bytes`); it runs in all three
modes (cold-start / bump / refresh). `fetch-favicon --check` only compares the
local file with the manifest (exit 1 on drift); the default write mode fails
closed on HTTP failure or a non-SVG response. A placeholder or half-written file
is caught before the build by `npm run verify:favicon` (offline) and
`verify:build-inputs`; the fix is to re-run `node tools/sync/fetch-favicon.mjs`,
not `git checkout`.

Four notes about the table above:

- **Build entry point**: the real work happens in `tools/build/index.mjs`, which
  runs `cli:build` → `docusaurus build` → `pagefind --site build` and sets its own
  10 GiB heap; `pipeline/build.mjs` is just a stable entry that forwards
  arguments and merges `--max-old-space-size` into `NODE_OPTIONS` (an existing
  flag is respected; `BUILD_HEAP_MB` overrides the heap size).
- **Tool source is committed**: `.gitignore`'s `build/` matches at any depth and
  would swallow `tools/build/`, so `!tools/build/` and `!tools/build/**` were
  added explicitly; the root `build/` is an output that is not committed,
  `tools/build/` is source.
- **Assertion wiring**: when adding an assertion, update `tools/verify/` and the
  `steps` in `tools/pipeline/verify.mjs` together (and wire the command into a
  `.github/workflows/pages.yml` job when CI enforcement is intended; there is no
  `ci.yml`); `verify:ui` needs
  `build/` + Chrome and is only run locally with `--browser`, never in CI. The
  hub-only `verify:build-image-prefix` scans `<img src>` in `build/blog` and
  `build/hardware`; `pages.yml` calls it after build and before `verify:deploy`
  to specifically catch bare `/img/…` prefix regressions.
- **Deploy gate order**: `verify:assets` (`tools/verify/asset-refs.mjs`) **must run
  after `build:slim`**. `slim` deletes
  `build/<locale>/{img,assets/images,assets/files}` and rewrites URLs back to the
  root copies; without slimming first, `asset-refs` reports "locale prefixes
  remain in the artifact" — a real but fixable state. Only after slimming does it
  assert "no prefixes in the deploy shape, no dangling references, no double-hash
  PDF names". `npm run verify:deploy` fixes these five steps (`slim` →
  `asset-refs` → `base-url-refs` → `orphan-assets` → `llms-links`) into one
  command; `pages.yml` calls the same four assertions directly after
  `build:slim` (without slimming again — see the "Deploy gate" section of
  `guides/CI.md`). Double-hash PDF names are not caused by `sync-pdfs`:
  `mdx-loader`'s `transformLinks` rewrites Markdown attachment links into
  `require()` and the `otherAssets` loader adds another hash to an already hashed
  name; therefore PDF links are always written as raw
  `<a href="/assets/files/…" target="_blank" rel="noopener">` (conversion:
  `tools/translate/lib/pdf-links.mjs`). The npm alias for `--plan` in the locale
  repository is `npm run translate:plan` (prints the stage list, writes nothing);
  this repository has no `translate:*` scripts.
- **Harvest comes first**: the legacy corpus has been deleted and the existing
  overlays are the only Chinese draft. The locale repository's `translate:harvest`
  (no such script here) aligns "English block → overlay Chinese block" by
  structural fingerprint before `apply` and writes the result into that
  repository's `work/translate/model-memory.json` (existing keys are not
  overwritten, conflicts counted separately); otherwise `apply` rebuilds pages
  with no memory into English. It prints
  `harvest coverage: hardware pendingBlocks before=… after=…`; use those numbers
  for coverage changes, without a hardcoded threshold. This repository has no
  `translate:harvest` script.

### The translation chain has a single stage list

The three `translate` entry points (`translate:apply`, `translate:derive`,
`pipeline:translate`) are **three selections of the same definition**, no longer
separate pass lists. All three entry points and the stage list below exist only in
the locale repository (`templates/locale-repo/tools/pipeline/`); this repository
has none of these scripts:

- defined in `tools/pipeline/translate-stages.mjs`; `PASSES` is written once in
  execution order and `modes` marks which chain a pass belongs to
  (`backfill-captured-at` exists only in the apply chain).
- `--mode=apply` matches the old `translate:apply` item by item (13 passes),
  `--mode=derive` matches the old `translate:derive` (12 passes); the default
  `both` (31 passes) = `harvest` + apply chain + derive chain + the tail that only
  runs in the whole pipeline (hardware headings, PDF, image addressing,
  label/CLI assertions). Because both chains run, the same pass appears twice in
  `both` mode; `--from` takes the **first** occurrence — to resume precisely, use
  `--mode=derive --from=<id>`.
- `--plan` only prints `=== <id>: <title>` and `$ node …` commands, writing
  nothing to disk or to the journal; `--dry-run` executes each stage's declared
  read-only form (`--check` / `--dry-run` / with `--apply` removed), and stages
  with no read-only form (such as `generate-ui`) are skipped with a note.
  `--check`-style assertions use exit 1 to mean "work remains", so a dry run
  continues through the remaining stages and exits non-zero in the summary.
- `--from=<id>` starts at that stage (after a failure, resume from the journal's
  `failed_stage`); `--only=<id>[,<id>]` runs only the listed stages.
  `--section=` / `--limit=` / `--locale=` are forwarded only to stages that
  declare `forwards`; others print an ignored notice.
- the journal is `.work/translate-run.json` (not committed):
  `{schema, started_at, git_head, mode, from, only, dry_run, stages:[{seq, id, title, command, status, exit_code, started_at, finished_at, duration_ms}], failed_stage?}`.
- to add a pass, add one entry to `PASSES` (`run: [script, argv]`, with `modes` /
  `forwards` / `dryRun` as needed): all three entry points stay in sync
  automatically; do not change `package.json`'s `&&` chain again.

## Locales

**There is only one source of truth**: `i18n.locales` / `i18n.defaultLocale` in
`docusaurus.config.ts`, resolved into `{locales, defaultLocale}` by
`resolveLocales()` in `tools/lib/site-config.mjs`. `config/mirror.yml` once had a
`locales:` list that no script read; it was deleted — do not add a second list.

All translate commands (including the `derive` chain and `verify`) accept
`--locale=<tag>`, defaulting to that repository's `DEFAULT_TARGET_LOCALE`
(authoritative copy `templates/locale-repo/tools/translate/lib/paths.mjs`, with a
different value per locale repository; this repository has none of these
commands); section and overlay paths always come from `sectionsFor(locale)`:

- `--locale=en` → error: it is the source locale (`i18n.defaultLocale`) and can
  never be a translation target;
- `--locale=<not configured and invalid format>` → error listing available
  locales (`en, zh-Hans`);
- a well-formed tag not yet configured (e.g. `ru-RU`) → only `--dry-run` /
  `--check` are allowed: probe the conventional paths without writing; it must
  be added to `docusaurus.config.ts` before anything is written, or an error is
  raised;
- `apply` / `derive` on a locale with "none of the four resources" simply return
  `files=0` instead of writing an English mirror of the whole site as that
  locale's overlay;
- `verify` itself is read-only, so any well-formed tag can be probed; a locale
  with no resources outputs 0 files and exits 0 instead of reporting thousands
  of missing items for "this locale hasn't started".

**derive (old → new version overlay)**: both `derive.mjs` and `derive-all.mjs`
accept `--locale`; the chain order is determined by `versions.json` /
`derivedFrom`, not by the locale. `--dry-run` is a real read-only form (takes
precedence over `--apply`, reports `apply: false` in the output, writes neither
overlay nor `state/translation-state.json`):

```bash
# run these in a locale repository; this repository has no tools/translate/derive-all.mjs
node tools/translate/derive-all.mjs --dry-run --locale=ru-RU   # read-only probe, 0 files written
node tools/translate/derive-all.mjs --apply --locale=ru-RU     # enable the locale before writing
node tools/translate/derive.mjs --from=docs-7.25 --to=docs --locale=ru-RU --dry-run
```

**verify (structural assertions)**: `node tools/translate/index.mjs verify`
without arguments still checks only that repository's default locale and its
output is byte-identical to the old version; `--locale=<tag>` checks one locale;
`--all-locales` walks the locales in `translatableLocales()` that **have
resources** (those without are skipped), runs the same assertions for each and
summarises them, exiting 1 if any fails. `--no-compile` skips MDX compilation
(faster for a read-only probe). All the commands below run in the locale
repository (this repository has no `tools/translate/index.mjs`):

```bash
node tools/translate/index.mjs verify                       # default locale, unchanged output
node tools/translate/index.mjs verify --locale=ru-RU        # one locale; 0 files, exit 0 when no resources
node tools/translate/index.mjs verify --all-locales         # the locale repo's npm run translate:verify:all
node tools/translate/index.mjs verify --all-locales --no-compile
```

**Naming conventions** (resolved only by `tools/translate/lib/paths.mjs`; other
scripts no longer concatenate strings):

| Resource | Path | Resolver |
| --- | --- | --- |
| overlay root | `i18n/<locale>/<plugin>[/current \| /version-<v>]` | `overlayRootFor(locale, section)`, `sectionsFor(locale)` |
| glossary | `config/glossary/<locale>.yml` | `glossaryFile(locale)` |
| page patches | `config/translation-patches/<locale>/<section>/<page>.yml` | `patchDir(locale)` |
| global TM | `work/translate/tm-global.<locale>.json` | `tmFile(locale)` / `tmFileFor(locale)` |
| known translations | top-level key `<locale>` in `config/known-translations.yml` | locale repository's `apply-known-translations.mjs --locale=<tag>` (no such script here) |
| llms.txt | `build/llms.txt` (source locale), `build/<locale>/…`; the full `llms-full.txt` is written by the plugin in the same directories per locale/version (`build/llms-full.txt`, `build/<locale>/llms-full.txt`, `build/docs/<v>/llms-full.txt`) | `tools/build/llms.mjs` walks `resolveLocales()`; full-text files are kept by `build:slim`, and only versioned copies not referenced by any `llms.txt` may be deleted (reported by default) |

Section-to-plugin mapping: `docs` / `docs-<version>` →
`docusaurus-plugin-content-docs` (with a `current` or `version-<v>` slot);
`hardware` → `docusaurus-plugin-content-docs-hardware` (with `current`);
`blog` / `changelog` → `docusaurus-plugin-content-blog` / `-blog-changelog` (no
slot; the blog plugin is not versioned).

**What adding a locale requires now**:

> This section describes operations inside the locale repository. This
> repository no longer hand-writes these configurations: for a new locale, use
> `npm run locale:add` to scaffold the entire locale repository from
> `templates/locale-repo/` (register `locales.json`, replace placeholders); see
> `templates/README.md`. The translate commands below all run in the locale
> repository; this repository's `package.json` has no corresponding scripts.

1. Add the tag to `i18n.locales` in `docusaurus.config.ts` and add label / htmlLang
   in `localeConfigs` — the only code location that must change;
2. create `config/glossary/<locale>.yml` (`terms: []` is enough at first): it
   marks "this locale has started" and keeps `apply` from being a no-op;
3. create `config/translation-patches/<locale>/` only if page-level exceptions
   are needed (not read when absent);
4. run in order (in the locale repository): `node tools/translate/harvest.mjs`
   (recycle the existing overlay; 0 for a new locale) →
   `node tools/translate/index.mjs apply --adopt --locale=<tag>` (generate the
   overlay from TM / model memory) →
   `node tools/translate/index.mjs translate --locale=<tag>` (the only step that
   calls the model);
5. for old → new version derivation:
   `node tools/translate/derive-all.mjs --apply --locale=<tag>` (confirm with
   `--dry-run` first; writing requires the locale to be enabled);
6. verify: `node tools/translate/index.mjs verify --locale=<tag>`, or the locale
   repository's `npm run translate:verify:all` to check every locale with
   resources in one run;
7. add UI copy: the `MANUAL` table in `generate-ui.mjs` and the navbar/footer
   strings are currently Chinese and need a version per new locale; likewise
   `INDEX_TEXT` in `tools/build/llms.mjs` (falls back to English, so a missing
   translation does not fail the build).

Four of these are hub-only structural gates, also chained into `npm run verify`:
the image-addressing prerequisite prevents "materialize drops `/img/<hash>` and we
only find out 54 minutes later when assets run"; two others prevent "`npm ci`
succeeded but a platform package entry is missing" and "the cold-start stage list
silently regressed"; the last turns archive artifact fidelity into an executable
assertion instead of a comment. See
[CI.md](CI.md#structural-gates-lock-integrity-and-cold-start-contract).

## Steps for adding a rule

1. **Data**: if it can live in configuration, put it in `config/`; if it can live
   in a manifest, put it in `data/manifests/`;
2. **stage**: add it to the stage list in `lib/update.mjs` (sync side) or to
   `PASSES` in the locale repository's `pipeline/translate-stages.mjs`
   (translation side);
3. **assertion**: add one under `tools/verify/` and wire it into `pages.yml` /
   `sync.yml` and the `npm run verify` entry point;
4. if any of the three is missing, it is only a one-off script in `tools/` and
   the work is not complete.

## One-off scripts

Some historical scripts remain under `tools/` (`restore-table-structure`,
`apply-sidebar-order`, `backfill-*`). They do not participate in CI and are not
guaranteed to be repeatable; to reuse one, first move its logic into the stages
and assertions above.

- A provenance backfill script adds the three front matter keys `translated_at` /
  `translation_provider` / `translation_model` to existing overlays: body text
  and existing keys are untouched, `translated_at` is the file's last commit
  time (falling back to the 7.26 fetch time when there is no history), `--check`
  only reports by default and `--write` is required to persist. It is not in this
  repository (`tools/translate/` no longer has the file), only in the locale
  toolchain: `templates/locale-repo/tools/translate/backfill-provenance.mjs`.

## Deliberate deviations from the official site

These are the places where the mirror intentionally behaves differently from
`manual.mikrotik.com`. They are written down because they look like bugs and the

- **`/docs/` and `/zh-Hans/docs/` use a client-side redirect; the official site
  returns 403.** The official docs use an index page with `slug: /` for
  `/docs/`; after `90c8473a` deleted that page (merging its content into
  `introduction.md`), the docs plugin only generates `/docs/<slug>` and no
  longer has a route for `/docs/` itself. But automatic language switching sends

  search all point back to `/docs/`, so it cannot 404 here.
  `src/pages/docs/index.tsx` therefore adds a `Redirect`: `/docs/` →
  `/docs/introduction`, `/zh-Hans/docs/` → `/zh-Hans/docs/introduction` (the
  language prefix is taken from the current path, not hardcoded `/zh-Hans`).
  The official `/docs/` returns 403 while we return a redirect — an intentional
